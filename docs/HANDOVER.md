## 0. 一页速览

**项目在做什么。** 从一段室内视频写出一份环境记忆。记忆里存每个可操作的小部件（把手、旋钮、按钮等）在哪里、怎么动。之后用一句话提问，记忆找到部件，并给出回答或三维动作向量。全程用现成模型加规则，不训练网络。主要评测数据是 SceneFun3D 的 30 个验证场景。

**现在在哪一步。** 项目负责人 11-20 定的六步计划（便宜的测试 → 冻结框架 → 端到端跑通 → 测各个 benchmark 合不合适 → 项目负责人选 benchmark → 针对性改进）里，前两步完成，第三步"端到端跑通"刚开始〔提案 §13、§17；笔记：experiment-plan-stages〕。项目负责人 11-23 说明：现在仍是完善 pipeline 的阶段，汇报的重心是 pipeline 的每一步，不是实验结果〔会话 11-23〕。

**11-25 的新优先顺序。** 项目负责人要求先找到这篇文章要解决的 gap，再做数据集和实验范围、affordance 提取两条线（第 1.1、6 节）。"端到端跑通"的后续工作因此搁置，等 gap 定了再看哪些还要做。找 gap 的计划已在 11-25 批准，在 issue AFFO-7 上进行。

**找 gap 阶段 1 的结论（11-25，等项目负责人选）。** 动作粒度的理解分三层：操作哪个部件、它怎么动、它现在是什么状态和什么被动过。前两层已被 2026 年的工作占住（找部件：UniFunc3D、AffordMem；怎么动：PhysGraph）。第三层在真实视频、部件这一层没有人做，而且 affordance map 在其中是必需的。总控推荐选第三层。详见第 5.8 节和 `docs/mem/gap调研_2026-11-25.md`。

## 1. 研究目标和当前的核心假设

### 1.1 方向

- **项目描述（Multica，2026-11-24）：** 在传统 video understanding 中加入 affordance map，避免完整 reconstruction 的冗余，同时保留与核心 action 相关的 3D 信息，帮助模型获得三维理解。
- **"避免重建"的表述（2026-11-24 定）：** 不训练网络，不依赖离线的稠密重建和激光扫描；只用设备自带的位姿和 LiDAR 深度，做一次约 15 分钟的逐场景高斯拟合。项目负责人选了这一表述，并同意据此改章程；章程还没改〔AFFO-1 评论 11-24，"2 a"〕。端到端跑通阶段里高斯图和体素对照的比较，仍可以改变"高斯为主体"这一点。
- **论文的落点和要先找的 gap（2026-11-25）。** 项目负责人的原话〔AFFO-1 评论 11-25〕："我这个pipeline的核心主要集中在了video understanding和相关的downstream task，我现在首先需要你做的就是探究一个合适的gap作为我这篇文章的解决核心。因为虽然说affordance map本质的添加我希望能够提高各种下游任务的准确性，但是它本身其实也还是更针对action层面，但是纯粹的environment understanding本身和action的细粒度是对不上的"。要找的是"最合理，最值得研究的点，能够融合affordance map优先"，并给出对应的数据集和 benchmark 候选。
- **gap 之后的两条线（2026-11-25）。** 一是数据集和最终实验范围；二是 affordance 的提取，原话："如果我想训练一个'grab the mug'，我希望他能够遇到任何一个叫做mug的东西都能够被抓取，因此需要他能够学习一些相关mug的抓取动作的feature，我希望探索如何进行这种动作的提取"〔AFFO-1 评论 11-25〕。边界已确认（11-25，"2 正确的"）：这条线在本项目里的产出是用于理解任务的 affordance 表示，对着标注和公开 benchmark 打分；让机器人去抓、看成功率属于 VLA 仓库。这条线可能需要训练，是否放开主旨 M5 的"不训练网络"，到调研结束时由项目负责人定。
- **关于 gap 的一条已确认的理解（11-25）。** gap 不能是"加了 affordance，各种任务都涨一点"；它要是一个本身就需要动作粒度（操作哪个部件、碰哪里、怎么动）、现有模型明显做不好的理解问题〔AFFO-1 评论 11-25，"2 正确的"〕。
- **项目负责人 11-10 的原话**〔章程〕："我构建的mem system包含的不只是semantic的内容更是每个object possible的action结果……我希望探索这种action的sequence或者human和obj的affordance map能不能辅助用来帮助构建mmeory system，这种变为4d的search效果是否会比传统静态3d搜索好"。并且"主要做memory system而不是robotics"。
- **定位：** 做记忆系统，不做机器人控制。VLA 方向在独立的私有仓库 `affordance-vla`，两边互不操作〔笔记：mem-branch-direction〕。
- **贡献类型：** 应用类。构建一条新的 pipeline，核心不完全在算法创新〔章程，2026-11-12 确认〕。
- **目标会议：** NeurIPS 2027 主会为主。是否先投 ICCV 2027 或 WACV Applications track，到关口 G2 再定〔章程〕。
- **使用场景：** 家里的使用指导、无障碍为主，家用机器人为补充〔笔记：mem-branch-direction，第 7 轮回答〕。

### 1.2 项目负责人的主旨（2026-11-18，现行）

原话〔差异记录〕："我其实希望能够立住affordance map这个部分，因为他是vector，本质是具有可解释性的，包括后面链接robotics的话其实也更加方便。我希望的是，通过affordance map的vector来辅助选择关键帧，但同时，这个affordance map本身是可以和后面需要的depth或者最终回答的action vector进行辅助计算的。另外就是，我希望之后在接大模型做open qa的时候能够确实是open qa而不是选择题。我希望我的这个affordance map的利用能够有两个header，一个用来接open QA，另一个用来输出具体的action vector，用来回答task的问题"

整理成六条，每次汇报都要逐条核对是"符合 / 没覆盖 / 偏移"〔笔记：main-idea-audit〕：

| 编号 | 主旨 |
| --- | --- |
| M1 | affordance map 是可解释的向量。最好是世界坐标里的真实三维向量，经一次刚体变换就能交给机器人（加分项，不强求） |
| M2 | 用 affordance 向量帮助挑关键帧 |
| M3 | affordance map 和深度一起算出最终的动作向量 |
| M4 | 两个头：真正的开放式问答（不是选择题），和输出动作向量 |

### 1.4 当前的核心假设

下面是「推断」：我从 v4 和已有结果归纳的、接下来要检验的假设。每条后面是现有证据。

1. **规则加现成模型能给出可用的部件三维动作向量。** 证据：给定部件时 48.8% / 38.4%，高于唯一的公开参照（粗略折算约 38.5% / 30.6%）〔提案 §13–14〕。只在标注掩码上测过。
2. **每个部件存"装在什么上"能解决最大的误差（运动类型）。** 证据：类型给对时升到 71.5% / 53.9%；只看部件名最多对 80.3%〔提案 §14；周报 2 第 3.3 节〕。"装在什么上"本身还没测。
3. **读少量帧的记忆比直接读原视频更准，优势在小部件和相似部件多的场景。** 证据：+5.6，小部件 +10.3，有同类部件 +6.6〔提案 §14〕。
4. **一个房间一张不训练的高斯场景图，能找回检测器漏掉的部件，并能在再次来访时局部更新。** 没有证据，阶段 2 要测。
5. **覆盖必须有条件。** 证据：场景不变时，"最新一帧说了算"会误删 14.4% 已找到的部件〔提案 §15〕。
6. **没有人做过"不训练、整屋、能在部件层更新、还存部件怎么动"的地图。** 这是 11-20 文献调研的结论〔提案 §15–16〕。**11-25 查新后不再完整成立：** PhysGraph（arXiv 2606.08655，2026-06）已经做了"不训练、整屋、存部件怎么动"，输入也是没有人操作的 RGB-D 视频加位姿，并在 SceneFun3D 的 30 个场景上报了数字；GEMS（arXiv 2610.33158，2026-10）做了"高斯记忆、再次来访时只更新变化区域、能问答"，但在物体一层。只有"在部件层更新"还空着〔`docs/mem/gap调研_2026-11-25.md` 第 6 节〕。

**冻结条款**〔提案 §17〕：场景图对外只有五个操作：建图、更新、查找、取视角、读部件。高斯图和体素对照用同一组操作。

**论文贡献的位置。** 助手 11-23 逐块讲解时的说法是：W5 部件向量、W6 场景图、W7 再访更新、R2 图上查找。项目负责人当时没有回应这一点〔会话 11-23〕。「推断」这还不算已确认。11-25 的调研显示，其中 W5 和 W6 的做法已被 PhysGraph 覆盖，W6 加 W7 在物体一层已被 GEMS 覆盖；如果项目负责人选了"部件的状态和变化"这个 gap，贡献会落在"沿运动轴读状态""按部件怎么动来更新"和问答头上（调研文档第 4 节）。

**存储形式的沿革。** 11-11 定的 L2 形式（每个关键帧的图，加部件 token 和薄的显式索引）〔讨论稿 §19〕是阶段 1 到公开评测用的记忆，代码在 `affordance3d/mem/tokens.py`、`search.py`。v4 的场景图要取代它，但 R2 的简化版现在仍在用 L2 这套检索。

### 9.2 GPU 和队列

- **允许的卡：0、1、4、5、6、7。永远不碰 2 和 3。** 唯一的例外是项目负责人对某一个任务点名，例如 11-20 的高斯试拟合用了 3 号卡。这种点名只对那一个任务有效〔笔记：a6000-server-access〕。
- **GPU 作业只走共享队列，** 不能绕过队列直接启动。队列是项目负责人另一个项目的队列程序，目录用环境变量 `AFFORDANCE3D_QUEUE` 指过去，不写进仓库。
- **排队脚本必须写明用哪些卡。** 队列自己的禁用列表是空的。本仓库的 `queue_*.sh` 都从 `scripts/remote/allowed_cards` 读卡号写进作业头（`#Q minmb=… share=… cards=…`），有测试检查。新的排队脚本必须照做〔commit 6c9518f〕。
- **一个作业只分到一张卡，** 不支持多卡作业。文件名前缀的数字越小越先跑。队列在给出的卡里挑显存最空的一张，不看顺序；要指定某张卡只能只写那一张。
- **每个研究目标单独批 GPU。** 2026-11-24 起，每个目标开工前报一个卡时上限和排队位置，由项目负责人批〔AFFO-1 评论 11-24，"5 a"〕。以前批过的"插到前面"都只针对当时的作业，不自动沿用。最近一次是 11-20：端到端跑通阶段的作业用前缀 100，排在项目负责人自己的作业前面。
- **已知的坑：** 8B 模型的作业用 `minmb=36000` 和 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。其他用户的进程会占满共享的卡，高斯批量拟合因此失败过 18 段。每个作业都要数日志里 `FAILED` 的行数。在服务器上按进程名杀进程会杀掉自己的连接，只能按 PID。
- **代码从不自动用 CUDA。** 只有队列作业设 `AFFORDANCE3D_DEVICE=cuda` 才用 GPU。
