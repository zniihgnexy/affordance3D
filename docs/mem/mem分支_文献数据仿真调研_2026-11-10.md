## 0. 结论先行

1. **"SceneFun4D"的核心想法已有相近工作，但正好缺我们最想做的部分。**
   - SceneFun3D 团队的 **FunRec**（CVPR 2026）已经从第一人称交互视频重建可动的功能数字孪生，并发布了真实数据集 RealFun4D：60 套公寓、351 段人与场景的交互。它做的是**重建**，不做记忆检索。
   - **GESTO**、**EGG**、**Embodied VideoAgent** 已经把带时间戳的人—物交互事件写进 4D 场景图或物体记忆，并用 LLM 查询。它们的粒度是物体，不是厘米级功能部件；也都不存"可能的动作及其结果"。
2. **"4D 优于静态"的直接证据很少，且规模小。**
   - 增益集中在时间类问题上，例如 EGG 去掉事件层后，时间类问题准确率从 0.78 降到 0.10。这在结构上必然成立。
   - 在以静态场景为主的 OpenEQA 上，加时间键只多 3.9 个点（R4）。
   - **没有论文在同一观察下比较"静态功能地图"和"加上动作→结果条目的同一地图"，也没有人测试"可能动作"类问题。** 这是讨论稿中 B2–B4 对照可以占据的位置。
3. **人类交互帮助发现功能部件有定量证据，但只针对可动整体。**
   - 示范轨迹使功能部件召回率从 55.8 升到 88.5（ArtiSG，3 个真实场景）。
   - 交互视频使可动部分 mIoU 从 23.7 升到 74.8（FunRec）。
   - 但交互主要暴露的是会动的门、抽屉，而不是旋钮、把手本身。在 SceneFun3D 的激光扫描尺度（每个部件约 106 点）上还**没有人测过**。
   - 静态方法在 SceneFun3D 上的上限很低：AffordBot 的 AP 只有 15.5，给真值掩码后 AP25 从 23.3 翻倍到 45.4。瓶颈在定位部件，H3 正好针对这一点。
4. **没有已发布数据在 SceneFun3D 场景里记录真实人体交互。** 真实线需要换数据：HD-EPIC 检验事件结构（H2），FunGraph3D 或 Hoi! 检验交互能否定位部件（H3）。
5. **人形可视化先走运动学路线**（LINGO 或 DartControl 生成 SMPL-X，viser 渲染）。物理人形方法大多依赖 Isaac Gym，在 RTX 5060 上跑不了。

**理论依据（各一句）：**
- Gibson 1979：affordance 是执行者与环境之间的关系，不是物体类别。
- [Zacks & Swallow 2007](https://pmc.ncbi.nlm.nih.gov/articles/PMC3314399)：运动变化触发事件边界，事件边界是长期记忆的锚点。
- Şahin 等 2007（*Adaptive Behavior*）：把 affordance 形式化为 (效果, (实体, 行为))，可以直接用作"动作结果"条目的键。

| 字段 | 建模它的工作 |
| --- | --- |
| 部件身份与几何（掩码、标签、所属物体） | SceneFun3D、FunGraph、AffordBot、ArtiSG |

| 效果对象（本地、远程，如开关 → 灯） | OpenFunGraph、Articulate3D 连接关系 |
| 状态变化（前后、包含关系变化） | VidOSC、SCHEMA、Lost & Found |
| 前提条件与程序上下文 | 可微任务图学习、Ego4D Goal-Step |
| 来源（交互时间窗、物体移动日志） | HD-EPIC、Lost & Found、Arti4D |

**FunGraph3D 补充核实（[数据卡](https://huggingface.co/datasets/OpenFunGraph/FunGraph3D)）：**

- **每个场景包含：**
  - 5 mm 激光扫描；

### SceneFun3D 的运动标注

来源：[标注文档](https://scenefun3d.github.io/documentation/dataset/annotations/)与本地 `421069_motions.json`。

- 每条记录有 `motion_id`、`annot_id`（链接到部件掩码）、`motion_type`、`motion_dir`（三维方向或轴）、`motion_origin_idx`（激光扫描上的轴原点索引）、`motion_viz_orient`（只是可视化提示）。
- 文档写的运动类型是 rotational／translational，实际文件里的取值是 `rot`／`trans`。
- **没有的内容：** 运动范围、当前或初始状态、时间戳、效果对象（开关控制哪盏灯）以及任何人体数据。官网第三项任务（motion estimation）的评测页仍显示"Coming soon"。

## 4. 仿真平台、人形交互合成与 Mac 上的可视化

**会改变计划的三点：**

- **Isaac Sim 的 README 把 RTX 4080 列为本地最低 GPU**，5060 低于这一要求。
- **Habitat 已停止维护。** Meta 在 v0.3.4 之后停止开发，habitat-sim 已归档。

### Mac 上渲染人形

- **[viser](https://viser.studio/main/embedded_visualizations)**（Apache-2.0）：有 SMPL 和点云示例；可以录制动画并导出为静态 HTML，嵌入 notebook 或网页。
- **[aitviewer](https://github.com/eth-ait/aitviewer)**（MIT）：支持 macOS，播放 SMPL/-H/-X 序列，有无界面模式，可导出视频。
- **Blender + SMPL-X 插件**：LINGO、TRUMANS、CHOIS、DART 都附带 Blender 脚本。
- pyrender 的离屏渲染在 macOS 上不可用；plotly／three.js 可以用，但每帧的人体网格要自己导出。

### 把静态扫描变成可动的场景

- **先自己做**：SceneFun3D 已经给了部件掩码和运动轴／原点。切出部件面片，用 yourdfpy 写 URDF 或用 usd-core 写 USD，静态部分用 CoACD 做凸分解。问题是扫描只看到抽屉面板，抽屉箱体要手工补。
- **[REACT3D](https://github.com/troyehuang/REACT3D)**（RA-L 2026，Delitzas 为合著者）：输入场景 .ply，检测可开启部分、估计关节、补全隐藏几何，导出 URDF；MIT。
- **[DRAWER](https://github.com/xiahongchi/DRAWER)**（CVPR 2025）：视频 → 带铰接门和抽屉的 USD；MIT。
- 物体级工具（Real2Code、URDFormer、Articulate-Anything、ACDC 等）不保留扫描几何，不适合。

### 推荐路径

**最便宜（运动学，不做物理）：**

1. 从 SceneFun3D 读取部件中心、法向和轴，在部件前约 0.5 m 的空地上选站立点（用体素化扫描检查是否空闲）。
2. **Mac 上的最小版本**：用简单的骨架或静态 SMPL-X 姿态 + 几步 IK，让手到达部件，不需要 GPU。
3. **在集群上用 LINGO 生成真实动作**：终点设为站立点，手部目标设为把手，扫描转成 LINGO 的占据栅格；DartControl 作为备选。
4. 从接触帧开始，按标注的轴转动或平移部件；逐帧记录 `(t, 动作, 部件 id, 关节值)`，这份日志就是 SceneFun4D 的事件记录。
5. 在 Mac 上用 viser 显示降采样点云、人体网格和转动的部件，导出 HTML；用 aitviewer 或 Blender 导出视频。

风险：LINGO 的训练场景与杂乱激光扫描之间存在差异；手部只能精确到厘米，旋钮没有手指动作；LINGO 没有许可文件。

**更物理：** 用 SceneFun3D 掩码和轴（或 REACT3D）构建 URDF/USD，在 Newton 或 Isaac Lab 3.0 上用 ProtoMotions 让物理人形跟踪上面的运动学动作，用接触力驱动部件关节；在 Mac 上先用 Genesis 或 Newton CPU 调试。风险：旋钮需要灵巧手，扫描得到的碰撞网格噪声大，以及上面提到的 GPU 兼容问题。

## 5. 对本分支的含义

### 与最接近工作的差异

| 工作 | 已经做了什么 | 留下的空白 |
| --- | --- | --- |
| FunRec / RealFun4D | 从交互视频重建功能数字孪生：可动部分、轴、逐帧状态、范围 | 只做重建，不做记忆、检索、问答；不处理长时间、多次交互的累积 |
| GESTO | 4D 场景图 + 带时间戳的人—物交互 + 事件层，用 agent 查询，并做了去掉事件层的消融 | 物体级；没有功能部件、可能动作及其结果；问题集仅 120 题 |
| Embodied VideoAgent | 动作驱动的物体状态记忆，在 EnvQA、OpenEQA、VQ3D 上评测 | 物体级；没有部件 → 效果的因果链；没有关闭动作更新的消融 |
| ArtiSG | 用人类示范构建带铰接参数的功能场景图 | 没有时间序列，也没有问答或检索评测 |
| OpenFunGraph | SceneFun3D 上的静态功能场景图，含远程控制关系 | 静态；可作为 B1 基线 |

**候选定位（待讨论）：部件级的 4D 功能记忆。** 每个厘米级功能部件同时保存三类信息：可能的动作及结果、实际发生过的事件、状态时间线；部分记忆由人类交互证据构建。在同一观察下，用 B1–B5 逐层对照，并加入目前没有人测试过的"可能动作／假设"类问题。领域进展很快（GESTO 发表于 2026 年 8 月，FunRec 于 2026 年 4 月），确定方向前需要再做一次新颖性检查。

### 对数据路线的影响

| 用途 | 首选 | 理由 |
| --- | --- | --- |
| 合成线（H1、H2、H4 的机制与可视化） | SceneFun3D 421069（本地已有） | 运动标注和 24 条"动作 + 效果"描述可以直接生成事件脚本 |
| 真实线 H2（事件结构帮助检索） | HD-EPIC 一个厨房 | 带时间的物体搬移、三维孪生和现成的 VQA；与本地 P28_101 格式相同 |
| 真实线 H3（交互帮助定位小部件） | FunGraph3D（SceneFun3D 同风格扫描 + 交互视频，免申请）；Hoi! 发布后作为可商用的补充 | 需要独立的部件真值；FunGraph3D 的交互视频没有时间标注和配准，需自己处理 |
| 记忆更新正确性 | ADT 一个序列 | 物体 6-DoF 真值精确 |
| 人形动作样例 | ParaHome | 真实的 SMPL-X 加铰接状态 |

"SceneFun4D"只是本分支的内部叫法。FunRec 已经用了 RealFun4D／OmniFun4D 这两个名字，对外写作时应避免混淆。
